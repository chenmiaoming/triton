# Stage G7 — Modal H100 上的 Gluon 基线实际验证

## 1. 结论

G6 的源码对齐基线已在实际 H100 上验证通过：

- 10 个实际推理工作负载与三个 LayerNorm merge 的 **26/26 次真实 CUDA tensor JIT 绑定**通过。实际编译产物与各自冻结 CUBIN、runtime ABI、constexpr、寄存器/共享内存配置一致；调用属性的无效空列表及额外真实对齐信息单列保留。
- 13 种 G6 冻结编译形式均加载到 GPU 运行。推理、独立 merge、完整 decode/backward 合计 **32 个配对计时条件**，三次独立 H100 调用，保留 **29,760 个原始样本**。
- **32/32 条件的配对 CI95 全部落入预注册 ±3% 实用等价带**。点估计 `100 × (G0/U − 1)` 为 **-0.612% 至 +0.629%**；所有区间端点总体落在 `-1.440%` 至 `+1.770%` 内。负数表示新 Gluon 更快，正数表示更慢。
- 校验阶段及三次计时运行合计 **300 项完整输出参考/输入/哨兵检查全部通过**。114 个必须位等的输出对照，以及 18 个相同 partial 输入的 merge 对照全部位等。

这支持将 `G0_source_aligned_v1` 作为**当前固定 H100、编译器、调用形式下**的对齐基线。它没有给旧 GL 候选重新背书；本阶段没有改变候选布局或测量新候选加速。

## 2. 运行范围与固定方法

使用 funded profile `chenmiaoming`，指定 `H100!:1`，实际设备均为 `NVIDIA H100 80GB HBM3`、SM90、132 SM。三次计时调用的 GPU UUID 不同，保存在 [timing_analysis.json](timing_analysis.json) 的 `environments` 中。驱动 API 版本为 13030；真实绑定任务记录的驱动版本为 `610.57.04`。

固定编译器 `20d9d98fead78c2f65e1b3ba5a7881d86a836dad`、native SHA `fc5f2ad73f9f8c8ab31c3a01b8124329ccec391cdc5dbf2dafb2d42778cf6adb`。G6 源码、既有 native 镜像和编译缓存直接复用，原生重编译为 0，ccache 统计未变，未安装任何编译后缀或后端 monkeypatch。

流程在观察计时结果前冻结：真实 tensor JIT 绑定 → 完整正确性 → 三次独立调用计时。计时进程通过 CUDA driver 加载冻结 CUBIN，不导入 Triton、不编译；每次 launch 前校验文件与内存中的二进制 SHA，分别保留 U/G0 的加载与运行记录，没有将同代码的两者去重或别名合并。

数据范围：

| 部分 | 条件 |
| --- | --- |
| 10 个实际推理 workload | vLLM 两种 tile × batch=1/8/64；SGLang d64/d128 × batch=1,length=256 或 batch=8,length=2048。SGLang 分别报告 stage1 与完整双核 decode。 |
| 其余默认调用检查 | 六个推理几何各用 batch=4,length=129；包含 vLLM s32/d128、SGLang d256 及默认 ABI。 |
| 训练 | 三种 LayerNorm 几何各测独立 dw/db merge，以及原始 dX + 新 merge 的 backward pipeline，full_M=128/2048。 |

累计 23 个推理条件、9 个训练条件。独立 merge 的真正输入行数为 `case.P`，并非表中历史 harness 标识 M=128；完整 pipeline 的 merge 行数为 `min(P, full_M)`。原始 cell 的 `kernel_M` 已明确记录。

计时使用单调用 CUDA Graph 的事件时间：三次调用 × 五次 visit × 每侧 31 个样本；每次 visit 随机交错 U/G0 顺序，各自八次预热。估计量是 3×5 个 visit 中位数的均值，配对 worker/visit 分层 bootstrap 4096 次。区间为逐点 CI95，无多重比较调整；±3% 是预先冻结的实用等价标准，不要求每个 CI 都含零。

## 4. 首轮绑定记录与修订

原始 [binding/attempt_001](binding/attempt_001) 完整保留，状态为 FAILED，没有改写成成功：

1. SGLang 的调用脚本遗漏了 `aux0_stride_*` 等仍在运行时 ABI 中的默认标量，八次调用在 warmup 前失败。这是本轮验证脚本错误，不是 Gluon kernel 编译错误。
2. 其余18次调用已经生成与冻结文件完全相同的 CUBIN/ABI/constexpr。部分 literal 属性字典含多余空列表；batch64 还比所复用的通用 batch8 编译元数据多一个真实的 `num_seqs % 16 == 0` 信息，但生成 CUBIN 完全相同。

在任何计时开始前写入 [protocol_v2.json](preregistration/protocol_v2.json)：补全 runtime kwargs；空列表只视为字面表示差异；batch64 额外对齐信息逐项用实际 batch 值核验，并要求完整 CUBIN/ABI/constexpr 仍相同。已有18份产物离线复核后复用，**只补跑缺失的八次 SGLang 绑定**，均通过。

[绑定汇总](binding_gate.json) 保留 literal equality、实际假设及其兼容依据；22次非空假设相同，四次 batch64 含额外真实对齐信息。没有放松 executable/ABI/资源相同要求，没有重选源码/候选，也没有根据计时挑选重复实验。
